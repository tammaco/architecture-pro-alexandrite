# Планирование: анализ, идентификация проблем и поиск решений

## Анализ

1. Увеличился срок выполнения заказов
2. Участились жалобы от операторов: когда они заходят на первую страницу MES, система долго прогружается
3. Значительные задержки релиза при деплое на продакшн
4. Добавились жалобы со стороны пользователей API (представители компаний ежедневно сообщают, что не получили свои заказы)
5. В release-окружения и продакшн версию деплоят вручную
6. Каждое приложение имеет по одному инстансу
7. Отсуствует база данных для заказов из CRM

Исходя из описания ситемы, самым узким местом явялется MES. Система не только долго рассчитывает стоимость заказа (может достигать 30 минут), но и медленно грузит первую страницу (жалобы от операторов). Также кажется нелогичным создание заказа в CRM от других продавцов через получение сообщения из очереди от MES. 

## Идентификация проблем

1. Нет единого источника статусов по заказам 
Изменение статусов размазано по нескольким системам. При интеграции через RabbitMQ легко потерять сообщение.

3. MES — самое узкое место

- Расчёт стоимости занимает до 30 минут - это создаёт огромную очередь.

- Онлайн-магазин и API ждут результата — это по сути синхронная связка через RabbitMQ

- Дашборд MES тормозит даже с фильтрацией и пагинацией — значит проблема глубже (неоптимальные запросы, отсутствие индексов)

3. Отсутствие мониторинга

- Жалобы на заказы при том, что производство загружено не на 100% говорит о том, что заказы просто не доходят до производства или теряются.

4. Проблемы с процессом взятия заказов операторами

- Дашборд MES тормозит и операторы физически не успевают вовремя их увидеть и забрать.

5. Ручное E2E и жёсткий критерий high/highest багов

- Ручное тестирование на двухнедельных спринтах - узкое место в QA, особенно при росте функционала.

- Запрет релиза при high/highest багах без учёта бизнес-рисков: задержки выросли с месяца до большего срока, хотя баги могут не влиять на критический путь. 

6. CRM + MES + RabbitMQ

- Интеграцию делали своей командой, но нет информации про мониторинг очередей.

- При росте заказов RabbitMQ может разрастись, сообщения могут накапливаться, а MES не успевает их разбирать.

7. Отсутствие метрик и алертов

- Не был  произведён анализ: среднее время от создания заказа до старта производства, время расчёта в MES, время нахождения заказа в очереди, процент потерянных сообщений.

## Поиск решений

### Инициативы (по приоритету)

1. Добавить в CRM свою БД

Сделать прозрачным процесс оформления заказов из всех систем, единым источником правды может послужить как раз новая БД.
MES, онлайн-магазин и API — только читают/обновляют статусы через CRM, а RabbitMQ использовать для асинхронного обмена.

2. Внедрить мониторинг очередей и времени прохождения заказа

Длина каждой очереди в реальном времени (Grafana + Prometheus) + алерт при превышении порогов.

3. Ввести ограничение на приём заказов через API (circuit breaker + очередь с приоритетами)

Установить размер очереди в RabbitMQ (например, > 1000 сообщений), среднее время ожидания расчёта (> 10 минут), процент ошибок при вызове MES (> 20%). Добавить приоритеты по классам заказов:

**high** - B2C заказы (онлайн-магазин, конструктор)

**medium** — ключевые B2B-партнёры (по договору)

**low** — новые / мелкие партнёры

CRM и MES слушают все очереди, но high разбираются первыми.
Одновременно для операторов можно добавить сортировку по приоритету.

4. Вынос расчёта в отдельные процессы

Расчёт не должен блокировать интерфейс, его нужно вынести в отдельный воркер (PriceCalculator).
Это не только повысит отзывчивость, но и даст возможность его перезапустить в случае неудачи.

5. Добавить кэширование в MES

Хранить в Redis списки по статусам, при каждом изменении статуса заказа обновлять соответствующий список.
MES будет быстро читать из Redis, пагинацию и фильтрацию делать на клиенте.

6. Добавить кэширование заказов для онлайн-магазина и партнёров

API Gateway - список заказов пользователя, статус конкретного заказа, базовую информацию о заказе, TTL: 1–2 минуты.
При любом изменении статуса (CRM отправляет событие в шину, кэш сбрасывается).

7. Автоматизировать регресс E2E

Из‑за ручного регресса баги находятся поздно, поэтому починка сдвигает дату выхода.
Нужно разделить баги на «блокирующие релиз» и те, которые можно фиксить в следующем спринте.

## Целевая архитектура через полгода

1. CRM — единственный источник правды

PostgreSQL хранит все заказы, статусы, временные метки переходов, приоритеты и публикует все события изменения статуса

2. Асинхронный расчёт стоимости

**PriceCalculator** — отдельный сервис (или набор воркеров). Результаты расчёта сохраняются в БД CRM.

3. Приоритеты на всех уровнях

Очереди RabbitMQ: high (B2C), medium (ключевые B2B), low (остальные)

Дашборд MES: сначала показывает high-заказы

Circuit breaker: при перегрузке отключает low-приоритет

4. Кэширование 

- API Gateway  - статусы заказов для B2C/B2B	(Cache-aside)
- MES	списки заказов по статусам (дашборд)	обновляется при изменении (Write-behind)

5. Мониторинг и алерты

Длина каждой очереди (high/medium/low) — алерт при > 500/1000/2000

6. CI/CD 

Автоматизированный E2E-регресс

Если бы у вас была возможность выполнить только три пункта из списка инициатив в ближайшие полгода, нужно выбрать первые 3 пункта, остальные не настолько критичны.
