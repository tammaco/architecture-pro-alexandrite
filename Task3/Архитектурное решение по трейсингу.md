# Анализ

На данном этапе необходим трейсинг для всех этапов обработки заказа, поэтому нужно покрыть системы его обработки.

|Система|Данные для трейсинга|Обоснование|
|-|-|-|
|Shop API|Данные клиента, состав заказа, 3d-модель (customer_id, order_id, session_id, file_hash, file_size)|Создание заказа от клиента, загрузка модели - главная входная точка B2C-клиентов|
|CRM API|order_id, status, message_id (для связки CRM и MES через очередь), retry_count - количество попыток отправки заказа|Подтверждение заказа, отправка в RabbitMQ, обработка результатов из MES|
|MES API|order_id, calculation_start_time, calculation_end_time, price_result, operator_id (кто взял заказ)|Расчёт стоимости — самое узкое место (2–30 мин)|
|Messages Queue (RabbitMQ)|trace_id, message_id, queue_name, publish_timestamp, consume_timestamp|Заказы теряются именно здесь|
|3D files storage (S3)|trace_id, file_hash, operation (upload/download), file_size_bytes, error_code (если есть)|Узкое место при загрузке/выгрузке моделей|

# Мотивация

**order_id** - сквозной параметр для идентификации заказа, передаётся во все системы.
**trace_id** - создаётся при первом запросе, должен быть в каждом сообщении.
**message_id** - должен логироваться из очереди вместе с order_id и trace_id.

При такой связке можно будет легко найти место, где заказ потерялся и не тратить часы на идентификацию проблемы.

## Технические метрики, на которые влияет трейсинг

1. MTTR — время от обнаружения проблемы до её устранения

Сейчас, чтобы найти причину потери заказа, нужно прошерстить разрозненные логи каждой системы (при наличии). С трейсингом в Jaeger по order_id можно увидеть полный путь за 2 минуты.

2. Пропускная способность обработки заказов

Например количество заказов, перешедших из SUBMITTED в MANUFACTURING_STARTED за час. Сразу будут выявлены узкие места.

3. Процент потерянных заказов 

Сразу можно будет определить количество сообщений в DLQ RabbitMQ исходя из общего количества отправленных сообщений.

## Бизнес-метрики, на которые влияет трейсинг

1. Customer Lead Time — время от создания заказа до отгрузки

Трейсинг выявит конкретные этапы, где заказы застревают.

2. Сокращение доли жалоб от операторов

Идентификация и устранение узких мест MES повысит удовлетворённость операторов.

3. Сокращение доли жалоб со стороны пользователей API

Быстрый поиск проблем ускорит их решение.

# Компромиссы

1. Сложность обучения команды

Понадобится время на интеграцию трейсинга во все сервисы и обучение разработчиков.

2. Ограниченный бюджет

Если на данном этапе узкое место уже обнаружено, трейсинг всех систем сразу может быть затратным, можно начать с очереди и MES.

# Аспекты безопасности

1. Настроить шифрование (TLS) для всех соединений

2. Контроль доступа

Закрыть операторам и продавцам трейсинг напрямую, настроит дашборды.
Полный доступ к интерфейсу и данным трейсинга только для сотрудников с выделенными ролями.

3. Все неиспользуемые порты должны быть закрыты

4. Маскирование чувтсительных данных

Личные данные клиента должны быть зашифрованы.
